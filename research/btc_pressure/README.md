# BTC Pressure V1 — event-driven research/paper implementation

**Это реализация исследовательского движка, а не подтверждённая стратегия +500% в год.**
Нет API-ключей, подписания запросов, отправки биржевых ордеров или подключения к
production scheduler. `live_ready=false`, годовая доходность неизвестна.

## Что реализовано

`record.py` записывает публичные Binance/Bybit WebSocket и REST ответы, ошибки,
отключения и heartbeat. Время обработки — локальное монотонное время получения,
привязанное к UTC. Биржевое время сохраняется отдельно: сортировка по нему не
создаёт задним числом ранние сигналы. SHA-256 защищает целостность записи, но сам
по себе не доказывает происхождение данных. HTTP 403/451 останавливает повторные
подключения к этому источнику, без обхода ограничений.

`adapters.py` нормализует сделки, стакан, минутные закрытые свечи, ликвидации и
контекст. Bybit orderbook snapshots заменяют состояние, delta содержит абсолютные
количества, ноль удаляет уровень. Порядок sequence проверяется без выдуманного
требования последовательности +1. Binance использует BBO/L1, **не полный L2**.

Bybit `allLiquidation.S=Buy` означает ликвидированный LONG: давление продаж.
Поле `p` — bankruptcy price, не наша цена исполнения. Binance forceOrder хранится
отдельно как sampled_1s, используется исполненное количество `z`, а не исходное
`q`. Наблюдения двух площадок не складываются в выдуманный полный рынок.

`strategy.py` реализует три детерминированных автомата состояний:
- `spot_trend`: подтверждение спотовым потоком обеих бирж, пробой закрытого часового
  диапазона, последующий ретест и восстановление. Пассивный вход; стоп и сопровождение
  по потоку, возможное удержание до семи дней без фиксированного тейка.
- `cascade`: локальный всплеск наблюдаемых ликвидаций, отскок, неудача отскока,
  продолжающееся давление и слабое восстановление противоположной стороны стакана.
- `absorption`: после каскада сохраняется агрессивный поток, но прекращается
  продвижение экстремума, восстанавливается глубина, затем подтверждается reclaim.
  Цель — область начала события, а не искусственная цена из будущего.

Правила проверяются для лонга и шорта. Поток агрегируется в секундные корзины из
реальных сделок; это не нанosecond/HFT и не восстановление стакана из свечей.
Глубина top-5 относительно предыдущей медианы — **эвристика восстановления**, не
доказанная модель очереди. Фиксированные пороги — исследовательские настройки,
не оптимальные параметры с доказанным ожиданием. OI/mark/funding читаются как
контекст; отдельная predictive OI/on-chain/ETF модель не реализована.

`paper.py` — один счёт и одна позиция, общий лимит риска. Добавления к убыточной
позиции и мартингейл отсутствуют. Перевод позиции в трендовое сопровождение не
увеличивает количество BTC; в calibrated mode требует собственного допуска.
Противоположный сигнал сначала закрывает позицию, а не открывает встречный
независимый счёт.

## Исполнение и ограничения риска

Post-only проверяется после задержки; касание не гарантирует исполнения.
Пассивная заявка ждёт видимую очередь и встречные сделки, без кредита за якобы
отменённые чужие заявки. IOC использует только записанную глубину с неблагоприятным
slippage; остаток не превращается в выдуманный market fill. Уже использованная
глубина не расходуется повторно на дубликате или изменении чужого уровня.

Частичное исполнение сразу получает защиту. Отмена имеет задержку и допускает
исполнения до подтверждения. Стоп инициирует reduce-only выход; цена берётся из
следующего доступного стакана после задержки, не из идеальной цены стопа.
Неисполненный остаток выхода остаётся открытым и явно отражается в отчёте.
При устаревшем стакане не создаётся фиктивное закрытие; результат помечается
`execution_incomplete`, новые входы блокируются. Потеря обязательных признаков
отменяет вход и инициирует выход из существующей позиции.

Экспериментальные значения по умолчанию: $1000, риск .25% на идею, cap 2x,
maker .02%, taker .05%, slippage .01%, latency 250ms, TTL 15s, участие в отдельной
пассивной сделке не выше 1% её объёма. **Это не подтверждённые настройки счёта
пользователя и не его фактические тарифы.** Размер/шаг/минимальный номинал инструмента
читаются из REST; без них новые сделки запрещены.

Риск уменьшается при DD 3%/5%, постоянная остановка при 7%, дневная при -1%.
Триггеры не гарантируют предел убытка при гэпе, отсутствии ликвидности или сбое.
Нет сертификации margin/liquidation модели. Cash сверяется с gross, fees,
реальным funding и остатком открытой позиции после каждого итогового replay.

Предполагаемый funding из ticker **не считается платежом**. Для платежа нужен
`settlement` с фактической ставкой и settlement mark. Автоматический сбор полной
истории таких платежей ещё не реализован. Пересечение неподтверждённого начисления
помечает результат неполным и инициирует закрытие; многодневный replay без этого
источника не является полноценной проверкой трендового режима.

## Три режима

`observe` (по умолчанию): обнаруживает сигналы, не открывает даже paper-позиции.
`diagnostic`: исполняет гипотезы после проверки данных/расходов/риска; это режим
исследования, **не заявление положительного математического ожидания**.
`calibrated`: дополнительно требует эмпирический допуск из более ранних данных
для данного family:side, той же площадки и настроек расходов: >=200 сделок,
>=30 дней, положительная нижняя оценка среднего net R по дням. Без калибровки
вход запрещён. Предыдущая выборка не может пересекать период replay.

`fit-gate` группирует чистый результат сделок по дням и выполняет day bootstrap.
Это исследовательская статистика без коррекции множественного отбора, не
вероятность успеха и не сертификат прибыльности. JSON-флаг происхождения данных
является утверждением поставщика; неизвестное происхождение не принимается
как реальное. Нужно отдельно проверять происхождение и пригодность архива.
Полный вероятностный оптимизатор действий из концепции не реализован: V1 использует
прозрачные автоматы состояний, приоритет событий и проверяемый эмпирический допуск.

## Что действительно протестировано

89 локальных тестов: направления ликвидаций, snapshots/deltas, dedup, причинность,
прогрев/пропуски, все три механизма в обе стороны, очередь, post-only, IOC,
partial fills, cancel race, стоп с гэпом, истечение котировок, реальные/предполагаемые
funding, ограничение экспозиции, reset состояния, калибровка и денежная сверка.
**Синтетические тесты доказывают поведение кода, не рыночную доходность.**

Реальная запись выполнена 5 сентября 2026, примерно 01:03:57–01:06:59 UTC,
workflow run `33934991785`, artifact `9959903621`. Записано 36 573 сообщений,
нормализовано 2 320 исполненных сделок, 33 770 обновлений книг/BBO, два наблюдения
Binance liquidation. Ошибок разбора при локальном replay нет.

Но Binance Spot/REST вернул 451, Bybit REST — 403. Не получены обязательный второй
спотовый поток, REST-прогрев и параметры инструмента; сама запись всего три минуты.
Полных feature frames и сигналов нет, сделки не открывались. Поэтому
`performance_evaluable=false`, `strategy_return_pct=null`, `cagr_pct=null`.
**Это не бэктест с нулевой доходностью. Это проверка обработки неполного потока.**

Первый recorder повторял отказ Binance Spot 77 раз; после проверки добавлено
прекращение повторов при 403/451. Исходный архив не исправлялся задним числом.
У исходного manifest нет нового поля synthetic; replay сохраняет неизвестное
значение, происхождение именно этого архива подтверждается capture workflow.

CI `BTC Pressure validation` отдельно проверяет новый модуль, весь корневой набор
`tests`, скачивает исходный artifact и повторяет replay для Binance и Bybit,
сверяя hash, counts, отсутствие parse errors и запрет оценки доходности.
Успех CI — инженерная проверка, не выполнение цели +500%.

## Запуск

Python 3.11+, CI использует 3.13. Из корня репозитория:

```bash
python -m pip install -r research/btc_pressure/requirements.txt
python -m pytest -q tests/test_btc_pressure.py
python -m research.btc_pressure.record --out pressure-capture-new --seconds 900
python -m research.btc_pressure.run replay --data pressure-capture-new --out pressure-report-new --mode diagnostic --venue bybit_perp
```

Capture требует законно доступных публичных endpoint. При отказе доступа запись
сохраняет ошибки, а не подменяет источник. Команды записи и replay конечные,
автоматический непрерывный live scheduler не подключён. Для уже приложенного
архива используйте его каталог `evidence`, новый уникальный каталог результата.

При наличии длительных проверенных diagnostic отчётов:

```bash
python -m research.btc_pressure.run fit-gate --reports prior-report-1.json prior-report-2.json --out prior-gate.json
python -m research.btc_pressure.run replay --data later-capture --out later-report --mode calibrated --calibration prior-gate.json
```

Выход: report.json с состоянием счёта, счетчиками/ошибками, журналом исполнения и
флагами полноты; trades.json только с закрытыми сделками. Прежние файлы отчётов
не перезаписываются. Это не адаптер реальной торговли, нет crash-recovery сервиса,
private order reconciliation и сертифицированного queue/margin replay.
